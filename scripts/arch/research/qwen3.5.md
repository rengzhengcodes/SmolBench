# Qwen3.5 (Alibaba) — architecture brief for the SmolBench family ladder

Scope: the three checkpoints this study served — `Qwen/Qwen3.5-27B`,
`Qwen/Qwen3.5-122B-A10B`, `Qwen/Qwen3.5-397B-A17B-FP8`.

**Ground truth** is `scripts/arch/arch_configs_raw.json` / `arch_facts.json` (fetched
2026-08-12, commit SHAs `fc05daec…`, `dc4d3484…`, `ea5b4f81…`). Everything else is named
and cited. Labels used throughout:

- **[C]** — read directly off the study's config JSON (ground truth).
- **[V]** — verified in a source file or paper I actually read (URL + line/section given).
- **[I]** — inference I drew; the reasoning is stated.
- **[U]** — claim I could not verify.

---

## Bottom line

All three rungs are the **same architecture at three sizes**: a Qwen3-Next-derived hybrid
stack that tiles `3 x (Gated DeltaNet -> FFN) + 1 x (gated GQA -> FFN)`, wrapped in a
Qwen3-VL multimodal shell. Rotary position information exists in **only 25% of the layers
and only 25% of each head's dimensions there**; the other 75% of layers are recurrent and
carry position implicitly. The ladder's one true architectural break is at rung 1: the 27B
is **dense**, the two larger rungs are **fine-grained MoE with a sigmoid-gated shared
expert**. Depth, width, expert count and top-k all move; the motif, head geometry, RoPE
scheme, norms and tokenizer do not.

---

## Family-level architecture (identical across all three rungs)

### The repeating motif

`layer_types` in every config is generated by
`"linear_attention" if bool((i + 1) % full_attention_interval) else "full_attention"`
([V] `configuration_qwen3_5.py` L112-117), so **full attention sits at layer indices
3, 7, 11, …** and the tile is:

```
[ GDN -> FFN ] x3  ->  [ GatedAttn -> FFN ] x1        (repeat)
```

Vendor model cards state the same motif in their own notation, e.g. the 397B card:
`15 x (3 x (Gated DeltaNet -> MoE) -> 1 x (Gated Attention -> MoE))` [V].
Independent confirmation from the FP8 checkpoint itself: `quantization_config.
modules_to_not_convert` lists a `linear_attn.*` submodule for every layer index **except**
3, 7, 11, …, 59 [C].

**Qwen never published an ablation for the 3:1 ratio** — the only Qwen source is the
Qwen3-Next release blog (*"When we mix Gated DeltaNet with standard attention at a 3:1
ratio … the model consistently outperforms any monolithic architecture"*) [V, vendor blog].
The independent literature does corroborate it, and shows it is not universal [V]:
**Kimi Linear** (arXiv:2510.26692) — a near-exact structural twin (gated-delta-rule linear
attention, 3:1, `fla` kernels) — published the ablation Qwen did not: val PPL **3:1 = 5.65**
vs 1:1 = 5.66, 7:1 = 5.70, 0:1 = 5.77, 15:1 = 5.82, concluding *"a uniform 3:1 ratio …
provided the best quality-throughput trade-off"*. Wang et al. (arXiv:2507.06457) recommend
3:1-6:1 for GatedDeltaNet specifically. Other hybrids sit far away: Jamba 1:7
(arXiv:2403.19887), MiniMax-01 7:1 (arXiv:2501.08313), Nemotron-H ~12:1 / 8% attention
(arXiv:2504.03624).

Every block is pure **pre-norm** with two residual streams and nothing else — no sandwich
norm, no `post_self_attn_layernorm` [V]:

```
h = h + Mixer(RMSNorm(h))        # Mixer = linear_attn OR self_attn
h = h + FFN(RMSNorm(h))          # FFN = SwiGLU MLP (dense) or MoE block
```

### Block A — `linear_attention` = Gated DeltaNet

**Published mechanism**: *Gated DeltaNet*, from Yang, Kautz & Hatamizadeh, "Gated Delta
Networks: Improving Mamba2 with Delta Rule", **ICLR 2025** (arXiv:2412.06464) [V]. The
paper's Table 1 gives the state update exactly:

```
S_t = S_{t-1} ( alpha_t (I - beta_t k_t k_t^T) ) + beta_t v_t k_t^T ,   o_t = S_t q_t
```

i.e. Mamba2's scalar decay `alpha_t` composed with DeltaNet's Householder erase-then-write
`(I - beta_t k k^T)`. `alpha_t -> 0` clears memory; `alpha_t -> 1` recovers the pure delta
rule [V, §1 and Table 1]. `S` is a matrix-valued state of shape
`[linear_key_head_dim, linear_value_head_dim] = [128, 128]` per value head — **constant in
sequence length**, which is why these layers have no KV cache.

Implementation in the shipped model (`Qwen3_5GatedDeltaNet`, subclass of
`Qwen3NextGatedDeltaNet`) [V, `modular_qwen3_5.py` L207-335]:

| projection | shape | role |
|---|---|---|
| `in_proj_qkv` | `hidden -> 2*key_dim + value_dim` | fused q, k, v |
| `in_proj_z`   | `hidden -> value_dim` | output gate `z` |
| `in_proj_b`   | `hidden -> linear_num_value_heads` | `beta = sigmoid(b)` (write strength) |
| `in_proj_a`   | `hidden -> linear_num_value_heads` | `g = -exp(A_log) * softplus(a + dt_bias)` (log decay) |
| `conv1d`      | depthwise, `groups = conv_dim`, kernel 4 | short causal conv over the **concatenated q|k|v** |
| `out_proj`    | `value_dim -> hidden` | |

Order of operations [V, L237-334]: `in_proj_qkv` -> depthwise causal conv1d(k=4) with SiLU
-> split into q/k/v -> q,k `repeat_interleave` to value-head count -> gated delta rule
(`torch_chunk_gated_delta_rule` on prefill, `torch_recurrent_gated_delta_rule` on
single-token decode, both with `use_qk_l2norm_in_kernel=True`) -> `RMSNormGated(out, z)`
which normalises then multiplies by `silu(z)` -> `out_proj`.

Head-count semantics, and why `linear_num_key_heads: 16` differs from
`linear_num_value_heads: 48/64` [C, V]:

```python
if self.num_v_heads // self.num_k_heads > 1:
    query = query.repeat_interleave(self.num_v_heads // self.num_k_heads, dim=2)
    key   = key.repeat_interleave(self.num_v_heads // self.num_k_heads, dim=2)
```

This is **GQA inside the linear layer**: 16 query/key heads are broadcast **3x** (27B,
48/16) or **4x** (both MoE rungs, 64/16) to meet the value heads. The recurrence then runs
as `linear_num_value_heads` independent `128 x 128` states that share a key/query basis.
`linear_conv_kernel_dim: 4` is a 4-tap causal depthwise convolution — a hard local window
of 4 tokens applied to q, k and v (but *not* to `z`, `a`, `b`) [V].

The paper's Fig. 1 block design puts SiLU + **L2 normalisation** on the q/k paths, SiLU on
v, plain linear on alpha/beta, and "normalization and gating before applying output
projection" [V, §3.4] — matching the implementation one-for-one.

Ancestry, all at peer-reviewed venues [V]: the delta rule in linear transformers comes from
Schlag, Irie & Schmidhuber, "Linear Transformers Are Secretly Fast Weight Programmers"
(ICML 2021); its chunkwise-parallel training from Yang et al., "Parallelizing Linear
Transformers with the Delta Rule over Sequence Length" (**NeurIPS 2024**, arXiv:2406.06484);
the scalar decay `alpha_t` from Mamba2/SSD, Dao & Gu, "Transformers are SSMs" (ICML 2024);
the data-dependent gating idea from Yang et al., GLA (ICML 2024).

**Kernel dependency worth noting for a serving diagram**: the fast path needs the optional
`causal_conv1d` and `fla` (flash-linear-attention, https://github.com/fla-org/flash-linear-attention)
packages; without them transformers "silently falls back to slower and more memory hungry
PyTorch ops" [V, HF model docs].

### Block B — `full_attention` = gated GQA with QK-norm

Grouped-query attention, `head_dim` decoupled from `hidden_size`, with a **sigmoid output
gate** [V, `modeling_qwen3_5.py`, class `Qwen3_5Attention`]:

```python
self.q_proj = nn.Linear(hidden_size, num_attention_heads * head_dim * 2, bias=False)
...
query_states, gate = torch.chunk(self.q_proj(h).view(*shape, -1, head_dim * 2), 2, dim=-1)
query_states = self.q_norm(query_states.view(hidden_shape)).transpose(1, 2)
key_states   = self.k_norm(self.k_proj(h).view(hidden_shape)).transpose(1, 2)
query_states, key_states = apply_rotary_pos_emb(query_states, key_states, cos, sin)
attn_output, _ = attention_interface(...)
attn_output = attn_output.reshape(*shape, -1).contiguous()
attn_output = attn_output * torch.sigmoid(gate)     # <-- attn_output_gate
attn_output = self.o_proj(attn_output)
```

So `attn_output_gate: true` [C] means: **`q_proj` is double-width and its second half is a
per-head, per-dimension gate applied elementwise to the SDPA output, immediately before
`o_proj`.** Nothing else in the block is gated. Published provenance: Qiu et al., "Gated
Attention for Large Language Models: Non-linearity, Sparsity, and Attention-Sink-Free",
**NeurIPS 2025 — Oral and Best Paper Award** (arXiv:2505.06708) [V]. The paper's gate
position "G1" is exactly this one: `Y' = Y ⊙ σ(X W_θ)` applied to the SDPA output before
`W_O`. Qwen3.5 uses the paper's **elementwise** (per-dimension) variant rather than the
headwise scalar, and derives the gate from the query projection. Measured effect the paper
reports: the attention sink falls from *"an average of 46.7% of attention scores across
layers directed towards the first token"* to **4.8%**, plus tolerance of larger learning
rates [V]. Evidence base: 30 variants, 15B MoE and 1.7B dense, 3.5T tokens.

**QK-norm**: per-head `RMSNorm(head_dim=256, eps=1e-6)` on q and k, applied **before** RoPE
[V]. The gate half is *not* normed. Qwen names its own source: the Qwen3 Technical Report
(arXiv:2505.09388) §2 states *"we remove QKV-bias used in Qwen2 and introduce QK-Norm
(Dehghani et al., 2023) to the attention mechanism to ensure stable training"* [V] — i.e.
"Scaling Vision Transformers to 22 Billion Parameters", **ICML 2023**, PMLR 202:7480-7512,
whose fix for divergent loss from near-one-hot attention logits is
`softmax[(1/sqrt(d)) · LN(XW^Q)(LN(XW^K))^T]`. Qwen3.5 substitutes **RMSNorm over
`head_dim`** for that LayerNorm, so it is a variant of the ViT-22B recipe, not a literal
reproduction [V].

No sliding window, no attention/logit softcapping, no attention bias
(`attention_bias: false`) [C].

### Positional encoding — the subtle part

`rope_parameters` is identical in all three configs [C]:
`{rope_type: "default", rope_theta: 1e7, partial_rotary_factor: 0.25,
mrope_interleaved: true, mrope_section: [11, 11, 10]}`.

1. **RoPE applies to `full_attention` layers only.** The decoder layer routes
   `position_ids` and `position_embeddings` exclusively to `self_attn`; the
   `Qwen3_5GatedDeltaNet.forward` signature does not even accept them, and no positional
   term appears in its body [V, `modular_qwen3_5.py` L365-395 and L224-230]. **75% of the
   stack has no explicit positional encoding at all.** Those layers carry position
   *implicitly*, by two mechanisms: the 4-tap causal depthwise conv (a hard local
   ordering window) and the strictly sequential recurrent state update, whose
   `alpha_t`-decay makes the state a recency-weighted summary.
2. **Partial rotary, 25%.** `dim = int(head_dim * partial_rotary_factor) = int(256*0.25)
   = 64`, and `inv_freq = 1/(1e7 ** (arange(0, 64, 2)/64))` gives **32 frequency pairs**
   [V, `compute_default_rope_parameters`]. `32 == 11 + 11 + 10` — the `mrope_section` sums
   exactly to the number of frequency pairs [C, arithmetic].
3. **The other 192 dims are untouched and concatenated back** [V, `apply_rotary_pos_emb`]:
   `q_rot, q_pass = q[..., :64], q[..., 64:]`; rotate `q_rot`; `cat([q_embed, q_pass])`.
   Those 192 dims are content-only **NoPE channels**. Two cautions on *why*:
   - **Origin is speed, not extrapolation.** The `rotary_pct = 0.25` convention traces to
     GPT-J-6B via GPT-NeoX-20B (Black et al., ACL 2022 BigScience workshop, pp. 95-136):
     *"we … apply it only to the first 25% of embedding vector dimensions … this strikes
     the best balance of performance and computational efficiency"* [V]. No extrapolation
     claim appears at the origin. Qwen's blog *does* claim partial rotary is "improving
     extrapolation to longer sequences", but publishes no ablation [V but vendor-blog only].
   - **Partial rotary is NOT p-RoPE.** Barbero et al. (ICLR 2025, arXiv:2410.06205) propose
     p-RoPE, which *truncates* the low-frequency end of the spectrum. Qwen's
     `partial_rotary_factor` does something different: `inv_freq = 1/(theta**(arange(0,64,2)/64))`
     spreads the **full** exponent range `[0,1)` across only 32 frequencies — it
     *subsamples* the spectrum coarsely rather than truncating it [V, arithmetic on the
     code I read]. Citing Barbero or the NoPE length-generalisation literature
     (Kazemnejad et al., NeurIPS 2023 — whole-model NoPE, small decoders, synthetic tasks)
     as justification for this field would be wrong.
4. **The three mrope sections are (temporal, height, width)** = `[11, 11, 10]` [V].
5. **Interleaved vs. chunked M-RoPE.** Original M-RoPE (Qwen2-VL, arXiv:2409.12191)
   "deconstruct[ed] the original rotary embedding into three components: temporal, height,
   and width" [V, verbatim], each getting a *contiguous band* of frequencies. The academic
   source for the interleaved fix is **Huang et al., "Revisiting Multimodal Positional
   Encoding in Vision-Language Models", arXiv:2510.23095**, which proposes MRoPE-Interleave
   under the guidelines "positional coherence, full frequency utilization, and preservation
   of textual priors" — this is the `(Huang et al., 2025)` that the Qwen3-VL report cites,
   and the correct citation for the mechanism [V]. The Qwen3-VL Technical Report
   (arXiv:2511.21631, §2.1) states this "results in an imbalanced frequency spectrum,
   which subsequent studies have shown to degrade performance on long-video understanding"
   and that they "redesign the frequency allocation by interleaving the t, h, and w
   components across the embedding dimensions… each spatial-temporal axis is uniformly
   represented across both low- and high-frequency bands" [V, quoted verbatim]. The
   implementation is a stride-3 scatter [V, `apply_interleaved_mrope`, docstring:
   *"Reorganizes frequency layout from chunked [TTT…HHH…WWW] to interleaved
   [THWTHWTHW…TT], preserving frequency continuity."*]: T keeps indices 0,3,…,30; H takes
   `slice(1, 33, 3)`; W takes `slice(2, 30, 3)`.
6. **For text-only input M-RoPE degenerates to ordinary 1-D partial RoPE.** The Qwen2-VL
   paper says so outright: *"For text inputs, these components utilize identical position
   IDs, making M-RoPE functionally equivalent to 1D-RoPE"* [V, verbatim]. Same in the code:
   in `Qwen3_5TextModel.forward`, absent position ids are built as
   `arange(seq_len).view(1,1,-1).expand(4, batch, -1)` — one text row plus three
   *identical* (t,h,w) rows [V]. vLLM goes further and strips the fields entirely for
   text-only serving [V, `vllm/model_executor/models/config.py`: *"Text-only Qwen3.5
   models use one-dimensional positions. Remove the M-RoPE fields inherited from the
   multimodal configuration."*]. Since the study ran `--language-model-only`, **M-RoPE was
   inert in this study** — the effective scheme was partial (25%) 1-D RoPE at theta 1e7 on
   one layer in four.
7. **No RoPE scaling was in play.** `rope_type: "default"`, and a direct raw fetch of
   `Qwen3.5-27B/config.json` confirms no `rope_scaling` / `factor` /
   `original_max_position_embeddings` key exists anywhere in the file [V]. The 1,010,000-token
   claim on the model cards is an **opt-in user edit** to `rope_parameters`
   (`rope_type: "yarn"`, `factor: 4.0`, `original_max_position_embeddings: 262144`) [V,
   `Qwen3.5-27B/raw/main/README.md`]. The study served 131,072 << 262,144 native, so
   nothing was scaled.

### Norms

- `Qwen3_5RMSNorm` is **zero-centred / Gemma-style**: `weight` is initialised to zeros and
  the forward is `output * (1.0 + weight.float())`, computed in fp32 and cast back [V].
  vLLM makes the equivalence explicit by aliasing `GemmaRMSNorm as Qwen3_5RMSNorm` [V, per
  the implementation lane].
- `Qwen3_5RMSNormGated` (inside the GDN only) is a *conventional* ones-initialised RMSNorm
  followed by `* silu(gate)` [V].
- eps `1e-6` everywhere [C]. Final `norm` before `lm_head`; `tie_word_embeddings: false` on
  all three rungs [C].

### Tokenizer

`vocab_size: 248320` (padded) on all three [C]; `tokenizer_class: Qwen2Tokenizer`,
`model_max_length: 262144` [V, `Qwen3.5-27B/raw/main/tokenizer_config.json`]. This is a
**new, larger tokenizer** than Qwen3's 151,936 — Qwen3-Next-80B-A3B still ships 151,936 [V,
its `config.json`]. Alibaba Cloud's launch post attributes the change to multilingual
coverage ("250k vs 150k" vocab, 201 languages) [V but SECONDARY — vendor blog, not a paper:
https://www.alibabacloud.com/blog/qwen3-5-towards-native-multimodal-agents_602894].
Control tokens sit at the top of the range: `bos/pad = 248044`, `eos = [248046, 248044]`,
`vision_start/end = 248053/248054`, `image = 248056`, `video = 248057` [C].

### MTP (multi-token prediction)

`mtp_num_hidden_layers: 1`, `mtp_use_dedicated_embeddings: false` [C]. The weights **are**
in the checkpoint — the FP8 `modules_to_not_convert` list names `mtp.fc`,
`mtp.layers.0.mlp.gate`, `mtp.layers.0.mlp.shared_expert_gate` [C].

- **HuggingFace transformers discards them**: `_keys_to_ignore_on_load_unexpected =
  [r"^mtp.*", r"^model.visual.*"]` [V, `modular_qwen3_5.py` L671].
- **vLLM implements them for speculative decoding** as a DeepSeek-V3-shaped MTP module:
  `fc: Linear(2*hidden -> hidden)` over `concat(norm(embed), norm(hidden))`, then one
  decoder layer hardcoded to `layer_type="full_attention"` (no GDN in the draft head), then
  a final norm [V, `vllm/model_executor/models/qwen3_5_mtp.py`, per the implementation lane].
- `mtp_use_dedicated_embeddings: false` is observable as the **absence** of
  `mtp.embed_tokens` / `mtp.lm_head` in the safetensors index — the head shares the main
  model's embedding and output matrices [V, `Qwen3.5-27B/model.safetensors.index.json`].
  No code in transformers or vLLM was found that *reads* the field [V — an honest
  not-found]; that `true` would ship dedicated tables is [I].
- **The shape is DeepSeek-V3's, not Gloeckle's.** Gloeckle et al., "Better & Faster LLMs via
  Multi-token Prediction" (**ICML 2024**, PMLR 235:15706) uses *n independent parallel heads*
  on a shared trunk. DeepSeek-V3 (arXiv:2412.19437 §2.2) explicitly departs — *"we
  sequentially predict additional tokens and keep the complete causal chain at each
  prediction depth"* — with module `h'_i^k = M_k [ RMSNorm(h_i^{k-1}) ; RMSNorm(Emb(t_{i+k})) ]`
  (Eq. 21), a **shared** embedding and output head. Qwen3.5's two config fields read cleanly
  against that: `mtp_num_hidden_layers: 1` = one sequential module (D=1);
  `mtp_use_dedicated_embeddings: false` = shared embedding [V]. vLLM implements Eq. 21 almost
  literally (`pre_fc_norm_hidden` / `pre_fc_norm_embedding`, concat, `fc: 2*hidden -> hidden`),
  with the concatenation order swapped. Qwen has published **no MTP paper**; the Qwen3
  Technical Report contains zero occurrences of "MTP", "multi-token" or "speculative" [V].
- **The study did not use MTP.** `EC2_DEPLOY_SPECS` passes no `--speculative-config`, so the
  MTP weights were dead on arrival [C, `smolbench/evals/providers/ec2.py`].

### Multimodal wrapper and what the text tower inherits

All three ship as `*ForConditionalGeneration` with a nested `text_config` and a
`vision_config` (27-layer SigLIP-2-style ViT, hidden 1152, patch 16, spatial merge 2) [C].
Weight prefix is `model.language_model.layers.N.…` [C, FP8 exclusion list].
`--language-model-only` sets all multimodal modalities to zero so the vision tower is never
built [V, vLLM]. What the text tower inherits from the wrapper:

1. **The rotary class**: `Qwen3_5TextRotaryEmbedding(Qwen3VLTextRotaryEmbedding)` — the
   M-RoPE machinery is structurally present [V, `modular_qwen3_5.py` L184] but, per §6
   above, collapses to 1-D for text.
2. **The tokenizer's vision control tokens** (4 ids), which simply never fire.
3. **Nothing else.** `deepstack_visual_indexes` is `[]` in all three configs [C], and the
   transformers class deletes the field outright (`deepstack_visual_indexes =
   AttributeError()`) [V] — so unlike Qwen3-VL there is **no DeepStack residual injection
   into the first LLM layers**. The text stack is unperturbed.

## Rung 1 — `Qwen3.5-27B` (dense)

1. **Identity.** Qwen3.5-27B, Alibaba/Qwen, released **2026-02-24** (second wave; the 397B
   flagship landed 2026-02-16) [V, QwenLM GitHub releases + model card]. **27B total
   parameters**, dense so all are active [V, model card]. Config-only reconstruction gives
   **26.9B**, a 0.3% match [I, arithmetic below]. **Apache-2.0** [V, card].
   `Qwen2Tokenizer`, vocab 248,320 [C/V].
2. **Positional encoder.** Partial RoPE, `partial_rotary_factor 0.25` -> 64 of 256 head
   dims rotated, 32 freq pairs, `theta = 1e7`, `rope_type: "default"` (no YaRN/NTK/llama3
   scaling) [C]. **Applied in 16 of 64 layers only**; the other 48 are Gated DeltaNet and
   have *no positional encoding* — position enters via the 4-tap causal conv and the
   recurrence order [V]. M-RoPE sections `[11, 11, 10]`, interleaved, inert for text [V].
   `max_position_embeddings: 262144`; served at 131,072 [C].
3. **Attention.** Two kinds.
   - `full_attention` x16: **GQA**, 24 Q heads / 4 KV heads (**group size 6**),
     `head_dim 256`. Note `24 x 256 = 6144 > hidden 5120` — the attention is *wider than the
     residual stream* [C]. QK-norm (per-head RMSNorm, eps 1e-6) before RoPE; sigmoid output
     gate from the double-width `q_proj` (5120 -> 12288) before `o_proj` [V]. No sliding
     window, no softcapping.
   - `linear_attention` x48: **Gated DeltaNet**, 16 QK heads / **48** V heads (broadcast
     factor 3), `head_k_dim = head_v_dim = 128`, conv kernel 4 [C].
4. **FFN.** **Dense** — `intermediate_size: 17408`, SwiGLU (`hidden_act: "silu"`), and the
   config contains **no** `num_experts` / `moe_intermediate_size` /
   `shared_expert_intermediate_size` field at all [C]. Confirmed structurally: the dense
   text config declares every MoE attribute as `AttributeError()` [V]. Every one of the 64
   layers has the same dense MLP.
5. **Other blocks.** Zero-centred RMSNorm (`1 + weight`), pre-norm only, eps 1e-6; final
   norm; untied embeddings (2 x 5120 x 248320 = 2.54B params in embedding + lm_head);
   1-layer MTP head present in the checkpoint, unused; **bf16, unquantised** [C].
6. **Motif.**
   `16 x [ GDN -> RMSNorm-preFFN -> SwiGLU ] x3 + [ GatedGQA(RoPE) -> SwiGLU ] x1`
   — precisely: `(L, L, L, F)` repeated 16 times, `L` = GatedDeltaNet block, `F` = gated
   full-attention block, each block being `pre-norm -> mixer -> residual; pre-norm -> MLP
   -> residual`. Vendor's own wording: `16 x (3 x (Gated DeltaNet -> FFN) -> 1 x (Gated
   Attention -> FFN))` [V].

## Rung 2 — `Qwen3.5-122B-A10B` (MoE)

1. **Identity.** Qwen3.5-122B-A10B, released **2026-02-24** [V]. **122B total / 10B
   activated per token** [V, card]. Config reconstruction: **122.1B total**, and **9.8B
   active** if both embedding tables are counted (9.0B without) — so the vendor's
   "activated" figure evidently includes the embedding/lm_head [I]. Apache-2.0 [V].
   Same tokenizer, vocab 248,320 [C].
2. **Positional encoder.** Identical scheme to rung 1: partial RoPE 25% (64/256 dims), 32
   freq pairs, theta 1e7, no scaling, M-RoPE `[11,11,10]` interleaved, inert for text.
   **Applied in 12 of 48 layers**; the other 36 have none [C/V]. `max_position_embeddings
   262144`, served 131,072 [C].
3. **Attention.**
   - `full_attention` x12: GQA **32 Q / 2 KV** heads — **group size 16**, a much more
     aggressive KV reduction than the 27B's 6. `head_dim 256`, so `32 x 256 = 8192` =
     **2.7x the hidden size of 3072** [C]. `q_proj` is 3072 -> 16384. QK-norm + sigmoid
     output gate as above.
   - `linear_attention` x36: Gated DeltaNet, 16 QK / **64** V heads (broadcast factor 4),
     dims 128/128, conv kernel 4 [C].
4. **FFN / MoE.** Every layer is sparse. **256 experts, top-8 routed, plus 1 always-on
   shared expert**; `moe_intermediate_size = shared_expert_intermediate_size = 1024`;
   SwiGLU experts [C]. Routing [V, `Qwen3_5MoeTopKRouter`]: bias-free
   `Linear(hidden -> 256)` -> **softmax over all experts** -> top-k -> **renormalise the
   top-k weights**. There is **no** DeepSeek-style sigmoid router, **no** per-expert
   `e_score_correction_bias`, **no** aux-loss-free balancing; load balance is the classic
   auxiliary loss with `router_aux_loss_coef: 0.001` [C], training-only. The shared expert
   is added with a scalar sigmoid gate, Qwen2-MoE style [V]:
   `out = experts(h) + sigmoid(shared_expert_gate(h)) * shared_expert(h)`, with
   `W_g in R^{1 x d}`, no bias. **This gate has no publication of any kind** — it is absent
   from the Qwen1.5-MoE blog and the Qwen2 Technical Report (which contains zero occurrences
   of "sigmoid") and exists only in `modeling_qwen2_moe.py`, inherited verbatim [V]. Cite it
   as code. Fine-grained segmentation + shared-expert isolation themselves come from Dai et
   al., DeepSeekMoE, **ACL 2024** pp. 1280-1297 [V]. `mlp_only_layers: []` [C] -> no layer is
   forced dense.
   Notable trajectory: the Qwen3 Technical Report states *"the Qwen3-MoE design **excludes**
   shared experts"* with 128 experts / 8 active [V]. **Qwen3.5 reverses that** — the shared
   expert is back and expert count is 2-4x higher — and no publication explains why.
5. **Other blocks.** Same norms/MTP/wrapper as rung 1. **bf16, unquantised** [C].
6. **Motif.**
   `12 x [ GDN -> MoE ] x3 + [ GatedGQA(RoPE) -> MoE ] x1`, i.e. `(L, L, L, F) x12`, with
   every FFN slot replaced by `{256-expert top-8 router} + {1 sigmoid-gated shared expert}`.

## Rung 3 — `Qwen3.5-397B-A17B-FP8` (MoE, FP8)

1. **Identity.** Qwen3.5-397B-A17B, released **2026-02-16** (family flagship); this repo is
   the official FP8 derivative [V]. **397B total / 17B activated per token** [V, card].
   Config reconstruction: **396.3B total, 17.3B active** (embeddings included) [I].
   Apache-2.0, no FP8-specific carve-out [V, `Qwen3.5-397B-A17B/raw/main/LICENSE` and the
   FP8 README]. Same tokenizer, vocab 248,320 [C].
2. **Positional encoder.** Identical to rungs 1-2. **Applied in 15 of 60 layers**; 45 have
   none [C]. Native 262,144, served 131,072 [C].
3. **Attention.**
   - `full_attention` x15: GQA **32 Q / 2 KV** (group size 16), `head_dim 256`,
     `32 x 256 = 8192` = 2x hidden 4096; `q_proj` 4096 -> 16384; QK-norm + sigmoid output
     gate [C/V].
   - `linear_attention` x45: Gated DeltaNet, 16 QK / **64** V heads (factor 4), 128/128,
     conv kernel 4 [C].
4. **FFN / MoE.** **512 experts, top-10 routed, 1 shared**, expert hidden 1024, shared
   hidden 1024, SwiGLU, softmax-then-top-k-then-renormalise router, `router_aux_loss_coef
   0.001` [C]. All 60 layers sparse (`mlp_only_layers: []`, and the FP8 exclusion list
   carries `mlp.gate` + `mlp.shared_expert_gate` for every index 0-59) [C].
5. **Other blocks.** Same norms/MTP/wrapper. **Quantisation is the distinguishing feature**
   [C]: `quant_method: "fp8"`, `weight_block_size: [128, 128]` (fine-grained block FP8),
   `activation_scheme: "dynamic"`, `act_per_tensor: false`, `weight_per_tensor: false`. Kept
   in **bf16**: `lm_head`, `embed_tokens`, every `linear_attn.conv1d` / `in_proj_a` /
   `in_proj_b`, every `mlp.gate` and `mlp.shared_expert_gate`, the whole vision tower, and
   `mtp.fc` [C]. That exclusion set is coherent: the two GDN gate projections are only
   `num_v_heads = 64` wide and feed an exponential, and the MoE routers are `hidden -> 512`
   argmax-sensitive — exactly the tensors where FP8 rounding would be structurally
   dangerous [I].
6. **Motif.**
   `15 x [ GDN -> MoE ] x3 + [ GatedGQA(RoPE) -> MoE ] x1`, i.e. `(L, L, L, F) x15`, all FFN
   slots being `{512-expert top-10} + {1 sigmoid-gated shared}`.

## What changes across the ladder

**Moves:**

| knob | 27B | 122B-A10B | 397B-A17B |
|---|---|---|---|
| `num_hidden_layers` | 64 | 48 | 60 |
| tiles of the motif | 16 | 12 | 15 |
| `hidden_size` | 5120 | 3072 | 4096 |
| FFN | **dense**, 17408 | MoE 256 / top-8 | MoE 512 / top-10 |
| `num_attention_heads` | 24 | 32 | 32 |
| `num_key_value_heads` | 4 | 2 | 2 |
| GQA group size | 6 | 16 | 16 |
| `linear_num_value_heads` | 48 | 64 | 64 |
| GDN broadcast factor | 3x | 4x | 4x |
| shipped precision | bf16 | bf16 | **block-FP8** |
| tensor parallel (study) | 4 | 8 | 8 |

Note the non-monotonicity: **the dense 27B is the *deepest* model on the ladder** (64
layers) and the *widest* residual stream (5120), because a dense model must buy capacity
with depth x width where the MoE rungs buy it with experts. Rung 2 is *narrower* than
rung 1 in every dimension except head count. Depth is not monotone either (64 -> 48 -> 60).

**Fixed across all three:** the `3:1` motif and `full_attention_interval: 4`; `head_dim
256`; `linear_num_key_heads 16`; `linear_key_head_dim = linear_value_head_dim = 128`;
`linear_conv_kernel_dim 4`; `attn_output_gate true`; the entire `rope_parameters` object
(`default`, `1e7`, `0.25`, `[11,11,10]`, interleaved); `max_position_embeddings 262144`;
`rms_norm_eps 1e-6`; `hidden_act "silu"`; `vocab_size 248320`; `tie_word_embeddings false`;
`mtp_num_hidden_layers 1` + `mtp_use_dedicated_embeddings false`; `mamba_ssm_dtype
float32`; the `*ForConditionalGeneration` wrapper + vision tower; Apache-2.0; and (for the
two MoE rungs) expert hidden size 1024, shared-expert hidden 1024, `router_aux_loss_coef
0.001`.

**Derived quantities that matter for a diagram** (bf16 KV, fp32 recurrent state, 131,072
served context) [I, arithmetic from config]:

| | KV cache/token | KV @131k | GDN state/seq (fp32) |
|---|---|---|---|
| 27B | 64.0 KiB | 8.00 GiB | 144 MiB |
| 122B-A10B | 24.0 KiB | 3.00 GiB | 144 MiB |
| 397B-A17B | 30.0 KiB | 3.75 GiB | 180 MiB |

The KV cache is **only** charged by the 25% full-attention layers; the GDN state is
constant in sequence length but paid per concurrent sequence. The 27B is the *most*
KV-expensive rung despite being the smallest — 16 full-attention layers x 4 KV heads
against 15 x 2 and 12 x 2.

The transformers implementation states the relationship as literal inheritance [V,

`Qwen3-Next-80B-A3B` [V, its config.json]:

| | Qwen3-Next-80B-A3B | Qwen3.5 |
|---|---|---|
| architecture | `Qwen3NextForCausalLM` (text-only) | `Qwen3_5*ForConditionalGeneration` (+ ViT) |

## Config fields resolved from the `derived.unclassified` bucket

The atlas tooling flagged four non-plumbing fields it could not classify. All four are
explicable, and three of them are **vestigial in this family**:

| field | value | verdict |
|---|---|---|
| `mamba_ssm_dtype` | `"float32"` | **Real and load-bearing, for vLLM only.** vLLM's `Qwen3_5*Config` verify-hook copies it into `cache_config.mamba_ssm_cache_dtype` when that is `"auto"`, pinning the **recurrent delta-rule state to fp32** while the conv state stays at model dtype [V]. The field appears in a Mamba-less config because vLLM implements the GDN layer inside `vllm/model_executor/layers/mamba/gdn/` on the Mamba2/SSD cache machinery. transformers has no such field but casts to fp32 inside the kernels anyway [V]. |
| `mtp_num_hidden_layers` | `1` | Depth of the MTP draft head. Not a spelling the tooling knows (`_MOE_KEYS` covers `num_nextn_predict_layers` / `mtp_num_layers`). See MTP section. |
| `mtp_use_dedicated_embeddings` | `false` | MTP head shares `embed_tokens` / `lm_head` with the trunk. **No consumer found in either transformers or vLLM** — see the flag below. |
| `mlp_only_layers` | `[]` | Legacy Qwen2-MoE field naming layers forced to use a dense MLP. **Dead**: transformers declares it `AttributeError()` and executes `del self.mlp_only_layers` in `__post_init__` for both dense and MoE text configs [V]. Its presence in the shipped JSON is inherited cruft; its value (`[]`) is inert either way. |

## Findings, contradictions and open flags

1. **`attn_output_gate: true` is inert in transformers.** `grep attn_output_gate` over
   `modeling_qwen3_5.py`, `modular_qwen3_5.py`, `configuration_qwen3_5.py` returns
   **nothing** — the double-width `q_proj` and the `* sigmoid(gate)` are unconditional [V,
   I ran this grep]. vLLM *does* read it (`getattr(config, "attn_output_gate", True)`,
   sizing qkv as `num_heads * (1 + attn_output_gate)`) [V, implementation lane]. Both
   readers agree on this checkpoint since the value is `true`, but a `false` config would
   be silently ignored by transformers and honoured by vLLM. Worth flagging as a real
   divergence between the two reference implementations.
2. **`mlp_only_layers: []` ships in a config where the loader deletes the field.** Harmless,
   but it means the JSON overstates what is configurable.
3. **`deepstack_visual_indexes: []` ships where the class removes the field entirely**
   (`AttributeError()` in `Qwen3_5VisionConfig`) [V]. Same pattern: Qwen3-VL cruft carried
   into Qwen3.5's JSON. Consequence for the atlas: **no DeepStack injection**, the text
   stack is clean.
4. **`mtp_use_dedicated_embeddings` has no located consumer.** Its effect is visible in the
   checkpoint (no `mtp.embed_tokens` / `mtp.lm_head` tensors) but no code was found that
   branches on it. Reported as an honest not-found rather than papered over.
5. **The vendor parameter headline excludes the MTP module** [I]. Config-only reconstruction
   of the trunk gives 396.3B / 122.1B / 26.9B against headlines of 397B / 122B / 27B.
   Adding the 1-layer MTP head (~6.5B on the 397B, ~2.4B on the 122B — it contains a full
   MoE block) would overshoot every headline. So "397B" counts the trunk only.
6. **"Activated parameters" appears to include the embedding tables** [I]: 122B rung gives
   9.0B active excluding them, 9.8B including — against a stated 10B; the 397B gives 16.3B
   vs 17.3B against a stated 17B. The larger figure matches better in both cases.
7. **A research lane reported the shipped `rope_parameters` as YaRN with `factor: 4.0`.
   That is wrong.** A direct raw fetch of `Qwen3.5-27B/config.json` confirms
   `rope_type: "default"` and no `rope_scaling` / `factor` /
   `original_max_position_embeddings` key anywhere in the file, matching our ground truth
   [V]. The YaRN block is the README's *recommended user edit* for >262k contexts. Recorded
   here because the error is easy to repeat.
8. **No Qwen3.5 technical report could be found** on arXiv as of 2026-08-12 — the launch
   post promised one. What exists is the *Qwen3.5-Omni* Technical Report
   (arXiv:2604.15804), a different (audio/video-native) sibling model. The official blog
   (`qwen.ai/blog?id=qwen3.5`) is a JS-rendered SPA that WebFetch could not read;
   `qwenlm.github.io/blog/qwen3.5/` 404s (the blog moved hosts). **Consequence: there is no
   peer-reviewed or vendor-paper source for Qwen3.5's own design decisions** — the
   architecture claims here rest on the config, the reference implementations, the model
   cards, and the papers for each borrowed mechanism. That is a real sourcing limit, not a
   gap I can close. Specifically, **five load-bearing design choices have no paper anywhere**
   — vendor blog, model card or code only: the 3:1 interleave ratio for Qwen; the claim that
   partial rotary aids extrapolation; the sigmoid shared-expert gate; Qwen's MTP module; and
   the router's score function / load-balancing scheme. Qwen3-Next itself has **no paper at
   all**, and the Qwen3.5 launch post cites none.
9. **`norm_topk_prob`, `decoder_sparse_step` and `scoring_func` are absent from the
   Qwen3.5 configs** although Qwen3-Next carried the first two [C/V]. The behaviours are
   now hardcoded (renormalise: always; every layer sparse: always; score function: softmax).
   A config-only reader would not be able to determine the router's score function — it had
   to be read from source. Worth noting for any atlas entry generated from configs alone.
10. **Not covered:** benchmark/eval behaviour, the vision tower's internals, post-training
    (the thinking-mode toggle is `enable_thinking` in `chat_template_kwargs`, default on,
    split server-side by `--reasoning-parser qwen3` [V, card]), and the FLA/CUTLASS kernel
    variants of the gated delta rule.

## How this study served them

From `smolbench/evals/providers/ec2.py` [C]: all three at `max_model_len 131072` with
`--reasoning-parser qwen3 --language-model-only --enable-prefix-caching`; `tp=4` for the
27B (tier B, 4x L40S), `tp=8` for both MoE rungs (tier C, 8x H100). `--language-model-only`
means the vision tower was never constructed, so M-RoPE degenerated to 1-D partial RoPE and
the served graph is exactly the text stack described above. No `--speculative-config`, so
the MTP head was unused. Query heads divide the TP degree exactly in both cases (27B:
24 heads / tp 4 = 6 per rank; MoE: 32 / tp 8 = 4 per rank). KV heads: the 27B's 4 divides
tp=4 exactly (1 per rank); the MoE rungs' 2 KV heads are **fewer than tp=8**, so vLLM
replicates them across ranks.
